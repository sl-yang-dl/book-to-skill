# Spike 对照:zhimaAi/BookToSkill vs 本项目七块骨架

> 目的:用同一本书《写作这回事》的同一段原文,并排看两种产物,验证 D7(差异化定位)。
> 方法说明:zhimaAi/BookToSkill 的 git 协议在本环境被限速无法 clone,且其流水线需一个 LLM 批处理后端才能真跑;
> 因此下方 BookToSkill 侧为其**契约级重建**(字段严格按 `references/indexing.md` 的 batch 协议),非实时执行产出。
> 原文段落取自《写作这回事》"工具箱·词汇"节(行 991 / 1013 / 1059)。

## 原文(同一段,两边都吃这段)

> 把常用的家伙放在上面。其中最常用的(写作的基本素材)是词汇。就词汇而言,你大可以满足于自己已经有的,丝毫不用妄自菲薄。就像妓女对害羞的水手说的:"你有多少不重要,甜心,怎么使用才重要。"(行 991)
> 他来到河上。河就在那里。(行 1013,海明威《大双心河》)
> 关于词汇,最糟糕的做法之一是粉饰语汇……这就好比给家养的宠物穿上晚礼服……记住,用词的第一条规矩是用你想到的第一个词,只要这个词适宜并且生动即可。(行 1059)

## A. BookToSkill 产物(JSONL 知识点索引,契约重建)

```text
DOC_TO_SKILL_BATCH_V1
BATCH batch-000001
CHUNK chunk-000345
POINT
TITLE 写作词汇观:量不重要,用法才重要
SUMMARY 金主张写作者应知足于已有词汇,不必刻意扩充;最忌"粉饰语汇"——用小短词本就好却换大词,犹如给宠物穿晚礼服。选词第一条规矩是用想到的第一个且适宜生动的词。
KEYWORD 词汇
KEYWORD 粉饰语汇
KEYWORD 选词
KEYWORD 写作工具箱
QUESTION 斯蒂芬·金对写作者扩充词汇量持什么态度?
QUESTION 什么是"粉饰语汇",金为什么反对?
EVIDENCE u991
EVIDENCE u1013
EVIDENCE u1059
END_POINT
END_CHUNK
END_BATCH
```

它的字段只有:`TITLE / SUMMARY / KEYWORD / QUESTION / EVIDENCE`(EVIDENCE 是源单元 ID,由脚本回还原文,**模型禁止写内容**)。

## B. 本项目产物(七块骨架,节选自 `samples/写作这回事/references/note.md`)

- **心智模型**:词汇放工具箱最上层;"你有多少不重要,怎么使用才重要"。
- **论证证据**:海明威"他来到河上。河就在那里。"(行 1013);"粉饰语汇 = 给宠物穿晚礼服"(行 1059)。
- **与我连接(块5,读者填)**:金主张极简词汇,和我"写作的书"里叶圣陶/夏丏尊反复讲的"文气、修辞"是否冲突?
- **可执行下一步(块6,读者填)**:下次写初稿,强制用第一个想到的词,不许换大词"提升档次"。
- **未解问题(块7,读者填)**:极简是否适用于需要文采的非虚构?金的"适宜生动"和修辞训练怎么调和?

## 对照结论(D7 验证)

| 维度 | BookToSkill | 本项目(七块骨架) |
|---|---|---|
| 服务对象 | Agent 检索(机器优先) | **你本人读懂 + Pi 加载**(双用) |
| 产物形态 | JSONL 知识点索引 + 检索脚本 | 薄 SKILL.md + references/note.md |
| 模型能否写理解 | **明令禁止**("Do not write content") | **要求**写连接/应用/疑问(块5–7) |
| 人读吗 | JSONL + 脚本,人不爱读 | 你自己也要看 → 人读友好 |
| 沉淀"与我关系" | ❌ 无字段 | ✅ 块5 |
| 沉淀"我能做啥" | ❌ 无字段 | ✅ 块6 |
| 沉淀"我不同意/追问" | ❌ 无字段 | ✅ 块7 |

**核心差异一句话**:它能产出"这本书讲了啥、问啥答啥",但结构上产不出"它和我已有的 X 有什么关系 / 我能拿它做啥 / 我哪里不同意"。这正是 D7 要的差异化——**人读友好 + 强制综合的读书笔记 skill,而非机器检索索引**。

**spike 结论:D7 成立。** 七块骨架里块 5–7 是 BookToSkill 在契约层面根本无法覆盖的,差异化定位有真实壁垒,不是自嗨。

- 等打通 `sl-yang-dl/skills` 的 `install.sh` 后,可把本项目笔记 skill 真正加载进 Pi,验证"双用"是否真的好用。
